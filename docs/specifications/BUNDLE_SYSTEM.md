# Система игровых бандлов

Статус: APPROVED 2026-10-30, решение 152 (ответы пользователя 1А, 2В, 3А, 4А); реализуется по этапам.
Что уже в коде — таблица «Этапы»; раздел с пометкой «этап N» описывает замысел, пока этап не сделан. ТЗ —
`bundles.md` в библиотеке проекта; анализ ТЗ, аудит нынешних данных, этапы с файлами, проверками и рисками —
`plan/architecture/bundle-system.md` там же. Как устроены данные сейчас — [DATA_MODEL.md](../DATA_MODEL.md),
загрузчик — [systems/content.md](../systems/content.md).

Система строится расширением нынешней модели данных: моды, бандлы, записи по схемам `SCHEMAS`, ссылки и
зависимости из них остаются, второго механизма рядом с ними нет. Добавляется то, чего не хватает ТЗ: явные
типы связей, граф с точной проверкой тупиков, рецепты шире, открытые станки и инструменты, старт и эпохи
данными, отчёты из данных.

## 1. Понятия и решения

- **Мод** — папка `content/<мод>/`; его id — пространство имён записей.
- **Бандл** — включаемая часть мода, папка с `bundle.yaml` (`animals/wolf`); мир помнит свой набор бандлов.
  Так слово значит в коде, сохранениях и на экране «Моды», и так остаётся (**решение 1А**).
- **Сущность** — то, что ТЗ называет бандлом: запись данных с `id`, видом, `title` и полями своего вида.
- **Связь** — поле записи со ссылкой на другую сущность; тип связи записан в схеме поля.
- **Граф** — сущности и связи загруженного набора; строится из данных, руками не пишется.
- **Эпоха** — ступень прогресса из раздела 7 ТЗ. Технологий и исследования нет (**решение 2В**): рецепты
  узнаются по материалам, как сейчас, а эпоха — метка, которую проверяет граф (раздел 9).
- Станки и инструменты — открытые классы и флаги данных; новое действие в мире (разделка, вспашка,
  стрельба) добавляется кодом вместе со своей механикой (**решение 3А**, разделы 7 и 8).
- Бандл, который только дополняет (предметы, рецепты), сам входит в уже созданный мир (**решение 4А**,
  раздел 14).

## 2. Хранение

Без изменений:

```
content/<мод>/mod.yaml                      id, title, version, api, requires, wants
content/<мод>/<бандл>/bundle.yaml           title, requires, wants
content/<мод>/<бандл>/data/<вид>.yaml       сущности
content/<мод>/<бандл>/{icons,models,sprites,textures,sounds}/
content/<мод>/common/                       общие ассеты мода
```

Бандл собирают вокруг главной сущности: предмет, его рецепты, его картинки (решения 146 и 147: рецепт лежит
у станка или инструмента, которым его делают). Ничего не переносится. Новые виды `starts` (этап 4) и `eras`
(этап 6) ложатся теми же файлами: `data/starts.yaml`, `data/eras.yaml`.

## 3. Id и имена

- Id — `мод:имя`; имя из строчных латинских букв, цифр и `_`, английскими словами. Внутри своего мода
  приставку можно не писать.
- Id уникален внутри вида. Ключ общего реестра — `вид/мод:имя`: предмет и рецепт каменного топора — две
  сущности с одним id `tools:stone_axe` (так уже сейчас).
- Заменить чужую запись можно только явно: `replaces: true` (вся запись) или `patch: true` (часть полей).
  Повтор id без этого — ошибка проверки (этап 2).
- Переименование — поле `was: [старые id]` в самой записи: старые сохранения переводятся без правки кода
  (этап 3). Таблицы `Items.RENAMED`, `Crafting.RENAMED`, `Mat.RENAMED` остаются для сделанных переводов.

| Что | Правило имени | Примеры |
|---|---|---|
| сырьё | существительное; руда — `<металл>_ore` | `log`, `branch`, `fiber`, `clay`, `copper_ore` |
| материал | существительное или `<материал>_<форма>` | `planks`, `cord`, `brick`, `copper_bar` |
| инструмент, оружие, броня | `<материал>_<вещь>`: `wooden_`, `stone_`, `copper_`… | `stone_axe`, `copper_sword` |
| станок | существительное; улучшенный — `<признак>_<станок>` | `workbench`, `kiln`, `forge` |
| рецепт | id предмета, если рецепт у него один; иначе `<предмет>_from_<вход>` | `stone_axe`, `charcoal_from_branch` |
| эпоха | одно-два слова | `primitive`, `bronze`, `iron` |
| класс инструмента или станка | одно слово | `axe`, `knife`, `hammer`, `loom` |
| метка (`tags`) | строчное слово | `primitive`, `metal` |

Проверка имён только предупреждает: нынешние id не меняются.

Примеры ТЗ в наших id: `resource.fiber.plant` — `resources:fiber`; `resource.wood.log` — `resources:log`;
`resource.wood.plank` — `materials:planks`; `station.workbench.basic` — `tools:workbench`; `world.tree.oak` —
дерево `plants:oak`; `animal.boar` — существо `animals:boar`; `tool.axe.stone` и `recipe.tool.axe.stone` —
предмет и рецепт `tools:stone_axe`.

Общие поля всех видов (этап 2): `description` — текст для игрока; `tags` — метки для отчётов и поиска (логику

необязательные; отчёт покажет, у кого их нет.

Тип предмета руками не пишется: категория (инструмент, станок, еда, лечение, посадка, блок, материал)
выводится из полей, как сейчас (`Items.category`), а «сырьё или изделие» — из графа (делает ли его рецепт).

## 5. Связи

Тип связи записан у каждого поля-ссылки в `SCHEMAS` (`rel`, словарь `Content.RELATIONS`) и читается от записи,
у которой поле, к записи, которую оно называет; где связь даёт действие рук, оно записано в `via`
(`Content.ACTIONS`). Тест не пропустит ссылку без типа (этап 2, сделано).

| Связь ТЗ | `rel` и `via` | Поля | Пример |
|---|---|---|---|
| `harvests_into`, `drops` | `drops`: `dig`, `mow`, `fell`, `gather`, `dig_out` | `materials.item`, `bonus`, `mow_gives`; `plants.gives`; `trees.log`, `seed`, `twig`; `bushes.fruit`, `twig`, `item` | ель даёт бревно, если свалить её топором |
| — (смена состояния) | `becomes`: `mow` | `materials.mow` | скошенная трава становится землёй |
| `builds` | `builds`: `place` | `items.place` | камень ставит ячейку камня |
| `grows_from` (обратная) | `grows_into`: `plant`, `sow` | `items.plant`, `sow`, `crop` | зерно — в колоски |
| `repairs` (обратная) | `repaired_with`: `repair` | `items.repair` | каменный топор чинят кремнем и верёвкой |
| `feeds` (обратная) | `feeds_on` | `creatures.likes` | |
| `located_in`, `spawns_as` | `lives_in`; у биома — `spawns` | `creatures.biomes`; `biomes.trees`, `bushes` | дуб растёт в лесу |
| `produces` | `produces` | `recipes.makes` | |
| `consumes` | `consumes` | `recipes.needs` | |
| `requires_station` | `requires_station` | `recipes.at` | каменный топор — на верстаке |
| `requires_tool` | класс инструмента, а не ссылка: в добыче — `materials.dig` и `hardness` с правилами рук, в рецепте — `recipes.tools` (этап 5) | | камень копает кирка силы 2 |
| нерасходуемое, побочное, `replaces`, `in_era` | придут с полями `keeps`, `also`, `serves` (этап 5), `era` (этап 6) | | |
| `crafted_by`, «где используется» | обратный обход графа, не хранится | | |
| `unlocks` | нет: рецепт узнаётся по материалам из `needs` (решение 9) | | |
| `equips`, `ammo_for`, `requires_power`, `powered_by` | заведены в словаре, поля придут с механиками | | |

Условия добычи (какой инструмент, какая сила) граф спрашивает у тех же функций, которыми играет игра
(`Tools.can_dig` в `src/shared/content/tools.gd` и такие же для рубки, выкапывания и сбора), а не
переписывает их у себя: граф не может разойтись с игрой.

## 6. Рецепты (этап 5)

```yaml
- id: stone_axe
  title: Каменный топор
  description: Рубит деревья и кусты.       # общее поле
  makes: stone_axe                           # результат
  count: 1
  also:                                      # побочные продукты, с шансом
    - {item: resources:chips, count: 1, chance: 0.5}
  needs: {resources:flint: 1, resources:branch: 2, materials:cord: 1}   # расходуется
  keeps: {tools:mould: 1}                    # нужно в сумке, не расходуется
  at: workbench                              # станок; годится и тот, что его заменяет (serves)
  tools: [knife]                             # классы инструментов; было одно поле tool
  wear: 1                                    # износ инструмента за изделие, 0 — как сейчас
  process: craft                             # craft, refine, smelt, cook — для графа и отчётов
  time: 5
  provisional: [needs, time]                 # общее поле
```

Предметов `chips` и `mould` нет, они здесь для примера.

- `needs` всегда расходуется, `keeps` и `tools` — никогда (инструмент только изнашивается на `wear`).
- Альтернативные ингредиенты — второй рецепт того же результата (`charcoal_from_branch`): явно, проверяемо,
  виден в окне крафта. Группы вида «любое топливо» придут вместе с топливом печей.
- Альтернативный станок — поле самого станка `serves`: улучшенный верстак с `serves: [workbench]` делает
  всё, что делает верстак, рецепты править не нужно.
- Шанс побочного продукта считается детерминированно от задания, чтобы сервер и клиент совпали.
- Открытие рецепта — как сейчас, по материалам (`knowledge.gd`); полей `tech` и `unlock` нет (решение 2В).
- Поля без механики (энергия, навык, ограничение по биому, качество) заранее не заводятся: каждое придёт со
  своей системой, тип связи для него уже есть в словаре.

## 7. Станки (этап 5)

Станок — предмет с `prop`: ставится из сумки на клетки 2×2. `prop` становится открытым словом, классом
станка. Особое поведение задают флаги, а не имена:

| Флаг | Что значит | Сейчас у |
|---|---|---|
| `storage: 16` | хранит вещи | сундука |
| `fire: true` | горит, тушится, разжигается топливом, обжигает | костра |
| `repairs: true` | у него чинят инструменты (сейчас `Workshop.REPAIR_AT`) | верстака |
| `serves: [станки]` | делает рецепты этих станков | — |
| `place_tool: hammer` | ставится, только если инструмент этого класса в сумке (ТЗ, раздел 6) | — |

Нынешние станки получают эти флаги, и поведение не меняется. Новый станок (сушилка, дубильная стойка, ткацкий
станок, наковальня) — одни данные: предмет, модель, иконка, рецепт самого станка и рецепты при нём. Твёрдые
части станка берутся по его модели. Топливо печей и энергия — механики эпох контента.

## 8. Инструменты (этап 5)

`tool` предмета — открытый класс. Движок знает работу пяти классов в мире: `axe` рубит деревья и кусты и
копает деревянные ячейки, `pickaxe` — камень и руду по твёрдости, `shovel` — грунт и выкапывает кусты,
`sword` — сбивает ягоды и режет высокую траву, `scythe` — косит дугой. Незнакомый класс (`knife`, `hammer`,
`saw`, `needle`) в мире работает как руки, а в рецептах — как требование. Новое действие в мире — код вместе
со своей механикой; класс к нему уже готов. Название класса в подсказке «Нужен инструмент: …» берётся из
данных (первый предмет класса), а не из `Crafting.TOOL_NAMES`.

Сила, скорость взмаха, прочность и починка — как сейчас. Матрица «инструмент × объект → что даёт»
(результат 7 ТЗ) строится отчётом по тем же правилам.

## 9. Открытие рецептов и эпохи (этап 6, решение 2В)

Технологий и исследования нет. Рецепт узнаётся, как сейчас: когда в сумке побывали все его материалы
(решение 9). «Открытие через предмет» из ТЗ — это и есть нынешнее правило; открытие событием придёт со своей
механикой, если понадобится.

Эпоха — ориентир, а не замок: в игре она ничего не запрещает, прогресс задают сами цепочки (из чего, каким
инструментом, на каком станке). Эпохи нужны данным — проверке и отчётам, там, где ТЗ говорит о
«технологическом уровне» и «технологическом дереве».

- Вид `eras` (в `core`): `id`, `title`, `description`, `order` (0, 1, 2…, без повторов).
- Поле `era` (ссылка на эпоху) у предмета пишется там, где вещь открывает ступень: станок, первый инструмент
  из нового материала, новый материал. У остальных эпоха выводится графом.
- Выведенная эпоха: рецепт — наибольшая из эпох всего, что он требует (`needs`, `keeps`, `at`, `tools`);
  добыча из мира — эпоха инструмента, который для неё нужен (руками — 0); предмет — наименьшая из эпох его
  источников, но не ниже записанной `era`.
- **Ошибка:** записанная эпоха ниже выведенной («вещь эпохи 1 требует вещь эпохи 3»).
- **Предупреждение:** длинная цепочка для ранней эпохи (ТЗ, раздел 19).
- Отчёт «карта эпох» (вместо дерева технологий, результат 8 ТЗ): по эпохам — станки, инструменты, материалы и
  параллельные ветки, которые в ней открываются.

| Порядок | Id | Эпоха (раздел 7 ТЗ) | Нынешний контент |
|---|---|---|---|
| 0 | `foraging` | выживание без инструментов | сбор руками, ветки, волокно, ягоды |
| 1 | `primitive` | примитивные инструменты | верёвка, верстак, костёр, деревянные и каменные инструменты, сундук, факел |
| 2 | `bone_leather` | дерево, кости и кожа | — (разделки и кожи нет) |
| 3 | `bronze` | керамика и ранняя металлургия | печь, кирпич, уголь, горн, медь, медные инструменты |
| 4 | `iron` | железный век | — |
| 5 | `steel` | сталь и развитое производство | — |
| 6 | `gunpowder` | порох и огнестрел, абстрактно | — |
| 7 | `electricity` | электричество | только если пользователь решит, что оно в концепции |

Этап 6 заводит записи эпох 0–3 (нынешний контент и ближайшая ступень) и решает по этой таблице, какие вещи
получают `era`; эпохи 4–7 появляются вместе со своим контентом.

## 10. Процессы (раздел 5 ТЗ)

| Процесс | Правило (код) | Данные | Сейчас |
|---|---|---|---|
| добыча | `src/shared/game/world_actions.gd`, `tools.gd`: копать, рубить, валить, косить, собирать, выкопать куст | поля материалов, деревьев, кустов, растений | есть |
| ручной крафт | `src/shared/game/workshop.gd` | рецепт без `at` | есть |
| станочное производство | `workshop.gd`, `src/shared/game/placed.gd` | рецепт с `at` | есть |
| плавка и обжиг | то же | `process: smelt` | есть, без топлива |
| строительство | `world_actions.place_at` (блоки), `placed.put_from_bag` (вещи) | `place`, `prop`, `place_tool` | есть; двери и стены-предметы — этап MVP «Строительство» |
| выращивание | `world_actions.plant` | `plant`, `sow`, `crop` | кусты и посев есть, деревья из семян — нет |
| животноводство | — | — | механика позже |
| готовка | рецепт у костра или печи | `process: cook` | есть |
| исследование | — | — | нет (решение 2В) |
| ремонт | `workshop.repair` | `repair`, флаг `repairs` | есть |

Каждый процесс — своё правило в `src/shared/game/` со своими полями; общий у них только граф. Если у растения и
зверя появится общая механика (например, «собрать продукт раз в сезон»), она выносится в одно правило, а не
копируется в каждую запись (раздел 12 ТЗ).

## 11. Граф, старт и проверки (этап 4)

Модуль `content_graph.gd` в `src/shared/content/` (общий: им же проверит моды сервер):

- **узлы** — все записи набора, классы инструментов и станков, «руки»;
- **рёбра** — из полей по пометкам `rel`; условия добычи — из правил `Tools`;
- **старт** — запись вида `starts` (`core:default`): сумка, лагерь у спавна (костёр; сундук добавляет его
  бандл патчем), позже умения рук (этап 7). Новый мир спавнится по той же записи, так что проверка и игра
  начинают одинаково (сейчас лагерь записан в `Placed.put_camp`);
- **анализ** — достижимость от старта с инструментами добычи и станками; циклы (сильно связные компоненты;
  блокирующий — тот, в который нельзя войти извне); источники и потребители каждой сущности; глубина и
  эпоха; цепочки от сырья до изделия.

Ошибки (валят CI):

1. Недостижимо со старта в полном наборе бандлов: что-то, что делает рецепт или даёт мир; станок или класс
   инструмента, на который ссылаются.
2. Блокирующий цикл. Ремонт, переработка и обратимые преобразования разрешены.
3. У предмета нет источника: ни мира, ни рецепта, ни старта. Особый источник (квест, покупка) пишется явно:
   `source: special`.
4. Класс инструмента или станка в рецепте не принадлежит ни одному предмету.
5. Записанная эпоха ниже выведенной (этап 6).
6. Молчаливый повтор id (этап 2). Схема и битые ссылки — как сейчас.

Предупреждения (в отчёт, CI не валят): тупиковая вещь (её не тратит ни один рецепт, и она ни для чего не
нужна: сейчас это жёлудь и шишка), станок с одним рецептом, две вещи с одинаковыми свойствами и назначением,
цикл переработки с прибылью (бесконечные ресурсы), длинная цепочка для ранней эпохи, метка, встреченная один
раз (вероятная опечатка).

Мир с частью бандлов: рецепт, чей станок или инструмент в этом мире не достать, не показывается. Проверка
каждого бандла отдельно (она уже есть в `tools/validate.gd`) следит, что мир без чужих бандлов работает.
Нынешняя `Crafting.reachable` считает бревно, камень и руду доступными без топора и кирки; с этапа 4 она и
валидатор идут через граф, а `tests/progress_test.gd` остаётся проверкой игрой.

## 12. Загрузка и регистрация

Порядок прежний: `Content` читает бандлы, `resolve` упорядочивает их и выключает лишённые зависимостей, записи
проверяются схемой, накладываются патчи, проверяются ссылки, реестры заполняются в
`Mods._refresh_registries` (добавится реестр старта). Граф строят только валидатор, отчёты и тесты: игре на
телефоне он не нужен, и загрузка мира не дорожает. Эпохи нужны только графу и отчётам, реестра в игре у них
нет. Новый вид данных добавляется как сейчас: схема в `SCHEMAS`, реестр с `refresh()` (если вид нужен игре),
строка в `_refresh_registries`, проверка в `tools/validate.gd`.

## 13. Отчёты из данных (этапы 3, 4, 6)

Генератор `content_report.gd` в `tools/` пишет отчёты из загруженных данных в `docs/generated/`; CI проверяет,
что они свежие, как `code-index.md`:

- `content-index.md` — реестр сущностей: id, название, вид, категория, эпоха, источники, число связей, статус
  проверки (результат 2 ТЗ; заменяет нынешний список того же имени, который пишет `tools/doc_index.py`, чтобы
  не было двух генераторов одного файла);
- `content-recipes.md` — реестр рецептов: входы, выходы, расход, инструменты, станки, эпоха, время,
  альтернативы (результат 3);
- `content-graph.md` — источники и потребители, общие ресурсы и что от них зависит, матрица инструментов,
  цепочки, карта эпох (результаты 4–8, схемы mermaid);
- `content-checks.md` — предупреждения проверки и баланса (результат 9).

## 14. Старые миры и дополняющие бандлы (этап 7, решение 4А)

Дополняющий бандл — тот, в котором только предметы, рецепты, эпохи, старт и звуки (нет ячеек, деревьев,
кустов, растений, биомов, зверей). Он сам входит в старый мир, где включён его мод, если мир его ещё не видел:
`world.json` запоминает, какие бандлы существовали при сохранении, поэтому бандл, выключенный игроком,
выключенным и остаётся. Земля и номера материалов не меняются. Ручной список в `src/client/save_game.gd`
(факел, метка `content` 9) больше не нужен. Бандл с ячейками, деревьями или зверями в старый мир не входит:
он меняет землю и номера материалов.

## 16. Правила качества

1. **Совместимость.** Старые сохранения открываются (`tests/save_test.gd`), игра проходит тем же путём
   (`tests/progress_test.gd`); то, что видит игрок, меняется только с согласия пользователя.
2. **Без дублей.** Новое строится на нынешних механизмах (виды, схемы, ссылки, патчи, роли); новый механизм —
   только если нынешний не подходит, с решением в журнале.
3. **Один формат.** Id и имена — по разделу 3; ссылка всегда по id, с типом связи в схеме.
4. **Нет тупиков и циклов.** С этапа 4 граф проверяет каждый PR: всё достижимо со старта, блокирующих
   циклов нет.
5. **Ссылки проверяются.** Схема, битые ссылки, тип связи у каждой ссылки, молчаливые повторы — ошибки.
6. **Игровые данные — не в коде.** Числа, списки и имена контента живут в YAML; движок знает классы и флаги,
   а по id называет только записи ядра.
7. **Расширяемость и баланс.** Предварительные числа помечены `provisional`; баланс — правка данных;
   альтернатива — ещё один рецепт, а не исключение в коде.
8. **Решения записаны.** Журнал `plan/README.md`, [DECISIONS.md](../DECISIONS.md), этот документ и таблица
   этапов обновляются в том же PR, что код.
9. **Тесты после каждого этапа.** Все проверки из `CLAUDE.md` (с этапа 3 ещё свежесть отчётов) и новый тест,
   который падает без нового кода.

## 17. Чего система не делает

- Технологий, очков и дерева исследования (решение 2В).
- Скриптов и правил в данных: новое действие в мире — код вместе с механикой (решение 3А).
- Новых ячеек до расширения атласа (Т1), нескольких руд до правки генератора.
- Механик охоты, одежды, урона, стрельбы, топлива печей, энергии: они приходят со своими эпохами контента.
- Массового контента: каталог эпохи сначала утверждает пользователь, потом её бандлы и рецепты.
