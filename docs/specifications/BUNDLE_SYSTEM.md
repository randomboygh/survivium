(PR #238–#248), каждый раздел описывает код, пометка «этап N» — каким этапом он пришёл. Сверено с кодом и

типы связей, граф с точной проверкой тупиков, рецепты шире, открытые станки и инструменты, старт и эпохи

## 1. Понятия и решения

- **Мод** — папка `content/<мод>/`; его id — пространство имён записей.
- **Бандл** — включаемая часть мода, папка с `bundle.yaml` (`animals/wolf`); мир помнит свой набор бандлов.
  Так слово значит в коде, сохранениях и на экране «Моды», и так остаётся (**решение 1А**).
- **Сущность** — то, что ТЗ называет бандлом: запись данных с `id`, видом, `title` (ключ `[<мод>.<вид>.<id>]`) и полями своего вида.
- **Связь** — поле записи со ссылкой на другую сущность; тип связи записан в схеме поля.
- **Граф** — сущности и связи загруженного набора; строится из данных, руками не пишется.
- **Эпоха** — ступень прогресса из раздела 7 ТЗ. Технологий и исследования нет (**решение 2В**): рецепты
  узнаются по материалам, как сейчас, а эпоха — метка, которую проверяет граф (раздел 9).
- Станки и инструменты — открытые классы и флаги данных; новое действие в мире (разделка, вспашка,
  стрельба) добавляется кодом вместе со своей механикой (**решение 3А**, разделы 7 и 8).
- Бандл, который только дополняет (предметы, рецепты), сам входит в уже созданный мир (**решение 4А**,
  раздел 14).

## 2. Хранение

Без изменений:

```
content/<мод>/mod.yaml                      id, title, version, api, requires, wants
content/<мод>/<бандл>/bundle.yaml           title, requires, wants
content/<мод>/<бандл>/data/<вид>.yaml       сущности
content/<мод>/<бандл>/{icons,models,sprites,textures,sounds}/
content/<мод>/lang/<код>.yaml, content/<мод>/<бандл>/lang/<код>.yaml   тексты ключей (docs/TRANSLATION.md)
content/<мод>/common/                       общие ассеты мода
```

Бандл собирают вокруг главной сущности: предмет, его рецепты, его картинки (решения 146 и 147: рецепт лежит
у станка или инструмента, которым его делают). Ничего не переносится. Новые виды `starts` (этап 4) и `eras`
(этап 6) ложатся теми же файлами: `data/starts.yaml`, `data/eras.yaml`.

## 3. Id и имена

- Id — `мод:имя`; имя из строчных латинских букв, цифр и `_`, английскими словами. Внутри своего мода
  приставку можно не писать.
- Id уникален внутри вида. Ключ общего реестра — `вид/мод:имя`: предмет и рецепт каменного топора — две
  сущности с одним id `tools:stone_axe` (так уже сейчас).
- Заменить чужую запись можно только явно: `replaces: true` (вся запись) или `patch: true` (часть полей).
  Повтор id без этого — ошибка проверки (этап 2).
- Переименование — поле `was: [старые id]` в самой записи: старые сохранения переводятся без правки кода
  (этап 3). Таблицы `Items.RENAMED`, `Crafting.RENAMED`, `Mat.RENAMED` остаются для сделанных переводов.

| Что | Правило имени | Примеры |
|---|---|---|
| сырьё | существительное; руда — `<металл>_ore` | `log`, `branch`, `fiber`, `clay`, `copper_ore` |
| материал | существительное или `<материал>_<форма>` | `planks`, `cord`, `brick`, `copper_bar` |
| инструмент, оружие, броня | `<материал>_<вещь>`: `wooden_`, `stone_`, `copper_`… | `stone_axe`, `copper_sword` |
| станок | существительное; улучшенный — `<признак>_<станок>` | `workbench`, `kiln`, `forge` |
| рецепт | id предмета, если рецепт у него один; иначе `<предмет>_from_<вход>` | `stone_axe`, `charcoal_from_branch` |
| эпоха | одно-два слова | `primitive`, `bronze`, `iron` |
| класс инструмента или станка | одно слово | `axe`, `knife`, `hammer`, `loom` |
| метка (`tags`) | строчное слово | `primitive`, `metal` |

Проверка имён только предупреждает: нынешние id не меняются.

Примеры ТЗ в наших id: `resource.fiber.plant` — `resources:fiber`; `resource.wood.log` — `resources:log`;
`resource.wood.plank` — `materials:planks`; `station.workbench.basic` — `tools:workbench`; `world.tree.oak` —
дерево `plants:oak`; `animal.boar` — существо `animals:boar`; `tool.axe.stone` и `recipe.tool.axe.stone` —
предмет и рецепт `tools:stone_axe`.

## 5. Связи

Тип связи записан у каждого поля-ссылки в `SCHEMAS` (`rel`, словарь `Content.RELATIONS`) и читается от записи,
у которой поле, к записи, которую оно называет; где связь даёт действие рук, оно записано в `via`
(`Content.ACTIONS`). Тест не пропустит ссылку без типа (этап 2, сделано).

| Связь ТЗ | `rel` и `via` | Поля | Пример |
|---|---|---|---|
| `harvests_into`, `drops` | `drops`: `dig`, `mow`, `fell`, `gather`, `dig_out` | `materials.item`, `bonus`, `mow_gives`; `plants.gives`; `trees.log`, `seed`, `twig`; `bushes.fruit`, `twig`, `item` | ель даёт бревно, если свалить её топором |
| — (смена состояния) | `becomes`: `mow` | `materials.mow` | скошенная трава становится землёй |
| `builds` | `builds`: `place` | `items.place` | камень ставит ячейку камня |
| `grows_from` (обратная) | `grows_into`: `plant`, `sow` | `items.plant`, `sow`, `crop` | зерно — в колоски |
| `repairs` (обратная) | `repaired_with`: `repair` | `items.repair` | каменный топор чинят кремнем и верёвкой |
| `feeds` (обратная) | `feeds_on` | `creatures.likes` | |
| `located_in`, `spawns_as` | `lives_in`; у биома — `spawns` | `creatures.biomes`; `biomes.trees`, `bushes` | дуб растёт в лесу |
| `produces` | `produces` | `recipes.makes` | |
| `consumes` | `consumes` | `recipes.needs` | |
| `requires_station` | `requires_station` | `recipes.at` | каменный топор — на верстаке |
| `requires_tool` | класс инструмента, а не ссылка: в добыче — `materials.dig` и `hardness` с правилами рук, в рецепте — `recipes.tools`, у станка — `items.place_tool` | | камень копает кирка силы 2, доски делают с топором |
| нерасходуемое | `requires` | `recipes.keeps` | форма нужна в сумке и не тратится |
| побочное | `produces` | `recipes.also.item` | с изделием выходит щепа |

| `crafted_by`, «где используется» | обратный обход графа, не хранится | | |

| `ammo_for` (обратная) | `consumes` | `items.ammo` | лук тратит стрелу |

переписывает их у себя: граф не может разойтись с игрой.

## 6. Рецепты (этап 5б, сделано)

```yaml
- id: stone_axe
  title: "[tools.recipes.stone_axe]"        # общее поле: ключ, текст — в lang/<код>.yaml
  description: "[tools.recipes.stone_axe.about]"
  makes: stone_axe                           # результат
  count: 1
  also:                                      # побочные продукты, с шансом
    - {item: resources:chips, count: 1, chance: 0.5}
  needs: {resources:flint: 1, resources:branch: 2, materials:cord: 1}   # расходуется
  keeps: {tools:mould: 1}                    # нужно в сумке, не расходуется
  at: workbench                              # станок; годится и тот, что его заменяет (serves)
  tools: [knife]                             # классы инструментов; было одно поле tool
  wear: 1                                    # износ инструмента за изделие, 0 — как сейчас
  process: craft                             # craft, refine, smelt, cook — для графа и отчётов
  time: 5
  provisional: [needs, time]                 # общее поле
```

Предметов `chips` и `mould` нет, они здесь для примера.

- `needs` всегда расходуется (забирается, когда работа встаёт в очередь), `keeps` и `tools` — никогда: их
  проверяют, пока работа идёт (`Workshop.waits_for`), инструмент изнашивается на `wear` за изделие, когда
  износ включён (тот, что в сумке первым из своего класса).
- Альтернативные ингредиенты — второй рецепт того же результата (`charcoal_from_branch`): явно, проверяемо,
  виден в окне крафта. Группы вида «любое топливо» придут вместе с топливом печей.
- Альтернативный станок — поле самого станка `serves`: улучшенный верстак с `serves: [workbench]` делает
  всё, что делает верстак, рецепты править не нужно.
- Шанс побочного продукта считается детерминированно от задания, чтобы сервер и клиент совпали: у каждой
  работы очереди свой номер (`CraftQueue.serial`, сохраняется с игроком), `Crafting.comes` смешивает id
  рецепта, номер работы и номер строки `also` в число 0..1 и сравнивает с шансом (`Crafting.outputs`).
- `process` (`craft` — изготовление, `refine` — переработка, `smelt` — плавка и обжиг, `cook` — готовка)
  игре ничего не задаёт; по нему группирует реестр рецептов (кто в каком процессе —
  [content-recipes.md](../generated/content-recipes.md)). Рецепт готовки или с тушей зверя растит навык
  Готовки или Охоты и даёт шанс лишней штуки (`Workshop.yield_role`, решение 164).
- Окно крафта показывает, что нужно в сумке (в подсказке «не расходуется»), каждый класс инструмента с
  износом за изделие и побочные продукты с шансом. Граф считает `keeps` и `tools` тем, что рецепт требует,
  побочное — изделием рецепта (путь `also`), в прибыльных кругах — по его доле; `Crafting.check` не
  пропускает `wear` без `tools`.
- Открытие рецепта — как сейчас, по материалам (`knowledge.gd`); полей `tech` и `unlock` нет (решение 2В).
- Качество (решение 181, `src/shared/game/quality.gd`): сделанное получает среднее качество материалов
  `needs`, но не выше потолка навыка работы (Ремесло или Готовка), станка (поле предмета `quality_cap`: костёр
  70, камин 90, остальные 100) и рецепта (`quality_cap`: деревянные кирка и коса — 30).
- Поля без механики (энергия, ограничение по биому, навык как условие рецепта) заранее
  не заводятся: каждое придёт со своей системой, тип связи для него уже есть в словаре. Навыки рецепты не
  закрывают (решение 164, 5Б).

## 7. Станки (этап 5а, сделано)

Станок — предмет с `prop`, который ничего не хранит и не мебель (`Items.is_station`): ставится из сумки на
квадрат клеток по срезу своей модели (16 вокселей — 2×2, 8 — одна клетка), лицом к игроку
([systems/crafting.md](../systems/crafting.md), «Размер и поворот»).
`prop` — открытое слово (тип поля `word`), класс вещи: по нему берутся модель и твёрдые части. Особое
поведение задают флаги, а не имена:

| Флаг | Что значит | Сейчас у |
|---|---|---|
| `storage: 16` | хранит вещи; такая вещь не станок | сундука, большого сундука, шкафов, бочки |
| `fire: true` | горит, тушится, разжигается топливом (`fuel_max`, `fuel_start`), обжигает | костра, камина (очаг — без ожога) |
| `repairs: true` | у него чинят инструменты | верстака |
| `serves: [станки]` | заменяет эти станки (ссылки на предметы): их рецепты делают и у него, и чинят, если чинят у них | камина (костёр) |
| `place_tool: hammer` | ставится, только если инструмент этого класса в сумке (ТЗ, раздел 6) | — |
| `claims: true` | центр территории того, кто поставил, и его команды (`Territory`, [territory.md](../systems/territory.md)) | межевого столба |
| `steps`, `door`, `window`, `furniture`, `seat`, `keeps`, `bedding` | лестница, дверь, окно, мебель (не станок), отдых рядом быстрее, еда в хранилище портится медленнее, постель (решения 159, 163) | лестницы, дверей, окон, мебели, постели |

Нынешние станки получили эти флаги, поведение не изменилось (`Placed`, `Workshop` спрашивают флаги, классы
по имени не называет никто, кроме перевода старых сохранений). Флаг у предмета без `prop`, `serves` не на
станок, `place_tool` класса, которым не является ни один предмет, — ошибки `Items.check`; граф знает, что
станок с `serves` заменяет названные, а `place_tool` нужен, чтобы его поставить. Новый станок (сушилка, дубильная стойка, ткацкий
станок, наковальня — так и сделаны) — одни данные: предмет, модель, иконка, рецепт самого станка и рецепты
при нём. Твёрдые части станка берутся по его модели. Топливо есть у костра и камина (поле `fuel` топлива,
`Items.fuel_in`); топливо печей и энергия — механики эпох контента.

## 8. Инструменты (этап 5а, сделано)

`tool` предмета — открытый класс (тип поля `word`). Движок знает работу шести классов в мире: `axe` рубит деревья и кусты и
копает деревянные ячейки, `pickaxe` — камень и руду по твёрдости, `shovel` — грунт и выкапывает кусты,
`sword` — сбивает ягоды и режет высокую траву, `scythe` — косит дугой, `rod` — удит (решение 154).
Оружие дальнего боя (копьё, праща, лук) — предметы с `range` и `ammo`, бьют зверей ([systems/wildlife.md](../systems/wildlife.md)).
Незнакомый класс (`knife`, `hammer`, `saw`, `needle`) в мире работает как руки (`Tools.of` даёт руки,
`Tools.WORLD_KINDS` — девять известных) и
не изнашивается там, а в рецептах и у станков (`place_tool`) — требование. Новое действие в мире — код вместе
со своей механикой; класс к нему уже готов. Название класса в подсказке «Нужен инструмент: …» берётся из
данных (`Items.tool_title`): ключ `[tool.<класс>]`, его тексты — в `content/core/lang/`, а класс мода — в `lang/`
этого мода (решение 186); `Crafting.TOOL_NAMES` больше нет.

Сила — сколько прочности снимает удар (дерево `hits`, зверь `health`); у ячеек `hardness` — ворота (сила не меньше),
`toughness` — прочность, по которой удар слабого инструмента длится дольше (`Tools.swing_time`); скорость взмаха,
прочность и починка — поля предмета; навык меняет руку, не инструмент (`docs/balance/GAME_BALANCE_DESIGN.md`). Матрица
«инструмент × объект → что даёт» (результат 7 ТЗ) строится отчётом по тем же правилам, таблицы времени и ударов —
`tools/balance_report.gd`.

## 9. Открытие рецептов и эпохи (этап 6, решение 2В, сделано)

Технологий и исследования нет. Рецепт узнаётся, как сейчас: когда в сумке побывали все его материалы
(решение 9). «Открытие через предмет» из ТЗ — это и есть нынешнее правило; открытие событием придёт со своей
механикой, если понадобится.

Эпоха — ориентир, а не замок: в игре она ничего не запрещает, прогресс задают сами цепочки (из чего, каким
инструментом, на каком станке). Эпохи нужны данным — проверке и отчётам, там, где ТЗ говорит о
«технологическом уровне» и «технологическом дереве».

- Вид `eras` (в `core`, `content/core/data/eras.yaml`; реестр `src/shared/content/eras.gd`): `id`, `title`,
  `description`, `order` (0, 1, 2…; две эпохи одного порядка — ошибка `Eras.check`), `depth` — до скольких
  шагов изготовления от старта ждать вещи эпохи (0 — не проверять; числа предварительные, `provisional`).
- Поле `era` (мягкая ссылка на эпоху, связь `in_era`) у предмета пишется там, где вещь открывает ступень:
  станок, первый инструмент из нового материала, новый материал. У остальных эпоха выводится графом.
- Выведенная эпоха (`ContentGraph.era`, тем же проходом по путям, что глубина): рецепт — наибольшая из эпох
  всего, что он требует (`needs`, `keeps`, `at`, `tools`); добыча из мира — эпоха самого раннего инструмента,
  который это может (руками — первая); поставленное стартом — первая; предмет — наименьшая из эпох его
  источников, но не ниже записанной `era`.
- **Ошибка** `early_era`: записанная эпоха ниже той, что дают пути к предмету («вещь эпохи 1 требует вещь
  эпохи 3»); сообщение называет, что именно её задерживает.
- **Предупреждение** `long_chain`: вещь глубже `depth` своей эпохи — длинная цепочка для ранней ступени (ТЗ,
  раздел 19).
- Отчёт «Карта эпох» в `docs/generated/content-graph.md` (вместо дерева технологий, результат 8 ТЗ): по
  эпохам — что её открывает (записанная `era`) и что в ней появляется по видам предметов, и схема «Ветки»:
  инструменты, станки и открывающие вещи по эпохам со стрелками от того, из чего каждая выходит прямо.
  Эпоха предметов и рецептов есть в реестрах `content-index.md` и `content-recipes.md`.

| Порядок | Id | Название (`title`) | `depth` |
|---|---|---|---|
| 0 | `foraging` | Выживание без инструментов | 2 |
| 1 | `primitive` | Примитивные инструменты | 6 |
| 2 | `bone_leather` | Дерево, кости и кожа | 8 |
| 3 | `bronze` | Керамика и ранняя металлургия | 10 |
| 4 | `alloy` | Бронза | 13 |
| 5 | `iron` | Железо | 14 |
| 6 | `steel` | Сталь | 15 |

Записи — `content/core/data/eras.yaml` (2026-11-05: семь эпох, 0–6). Что открывает каждую (жирным) и что в
ней появляется — «Карта эпох» в [content-graph.md](../generated/content-graph.md), её пишет
`tools/content_report.gd`, так что таблица здесь не повторяет содержимое. Ступени раздела 7 ТЗ после стали
(порох, электричество) записей не имеют: появятся вместе со своим контентом, если пользователь их утвердит.
Разметку можно поправить одной строкой `era` у предмета.

## 11. Граф, старт и проверки (этап 4)

Модуль `content_graph.gd` в `src/shared/content/` (общий: им же проверит моды сервер; `ContentGraph.new()`
строит граф набора, загруженного сейчас):

- **узлы** — все записи набора, классы инструментов и станков, «руки»;
- **рёбра** — из полей по пометкам `rel`; условия добычи — функции `Tools` (`can_dig`, `can_chop`,
  `can_dig_out`, `can_gather`, `mows`), которыми решают и руки в `world_actions.gd`;
- **старт** — запись вида `starts` (`core:default`, реестр `Starts`): сумка (`bag`), лагерь у спавна (`camp`:
  костёр; сундук добавляет его бандл патчем `camp+`) и умения рук (`hand_power`, `hand_area`, `hand_swing`,
  `hand_reach`, `hand_mows`, `hand_slow`: `Tools.HAND`, этап 7б). Новый мир начинается по той
  же записи (`Placed.start_camp`, `Character.start_bag`), так что проверка и игра начинают одинаково;
- **анализ** — достижимость от старта с инструментами добычи и станками; циклы (сильно связные компоненты;
  блокирующий — тот, в который нельзя войти извне); источники и потребители каждой сущности; глубина и
  эпоха; цепочки от сырья до изделия.

Как граф идёт (сделано, этап 4б). Мир даёт все биомы, клетки, которые генератор кладёт (ядра и ролей; ствол
и крона — дерево, его рубят), растение каждого вида и растения со своей картинкой, существ без биомов; биом
даёт свои деревья (если в наборе есть роли ствола и кроны) и кусты. Действие над записью мира даёт вещи её
полей с `via`, если инструмент, что уже есть, это может по правилам `Tools` (руки — всегда в сумке). Рецепт
делается, когда есть его материалы, поставленный станок (`placed/<предмет>`: предмет с `prop` есть — его
можно поставить) и инструмент нужного класса; поставленное, посаженное и посеянное даёт свою клетку,
куст или растение. Так до неподвижной точки. Глубина: что мир и старт дают руками — 0, добытое
инструментом — глубина самого раннего инструмента, который это может, изделие — на 1 больше самого
глубокого из материалов, станка и инструмента рецепта. Каждое поле-ссылка записано в `ContentGraph.LINKS`
(что эта связь значит для графа): новое поле без строки там валит `graph_test`.

Ошибки (валят CI):

1. Недостижимо со старта в полном наборе бандлов: предмет, рецепт; станок или класс инструмента, на который
   ссылаются. Сообщение называет каждый путь и чего ему не хватает.
2. Блокирующий цикл. Ремонт, переработка и обратимые преобразования разрешены: цикл ищется только среди
   недостижимого (что чего не хватает), так что круг через достижимые вещи ничего не блокирует.
3. У предмета нет источника: ни мира, ни рецепта, ни старта. Особый источник (квест, покупка) пишется явно:
   `source: special`.
4. Класс инструмента в рецепте не принадлежит ни одному предмету; станок рецепта — не станок
   (`Crafting.check`).
5. Растение, куст или дерево не растёт в мире: ни один биом его не растит, его не сажают и не сеют
   (или то, чем сажают, не достать); у животного не растёт ничего из того, что оно ест (`likes`).
6. Записанная эпоха ниже выведенной (этап 6).
7. Молчаливый повтор id (этап 2). Схема и битые ссылки — как сейчас.

Предупреждения (в отчёт, CI не валят): тупиковая вещь (её не тратит ни один рецепт, и она ни для чего не
нужна: сейчас это жёлудь и шишка), станок с одним рецептом, две вещи с одинаковыми свойствами и назначением,
цикл переработки с прибылью (бесконечные ресурсы; прочие материалы рецептов круга не считаются), клетка,
которая не встречается в мире, длинная цепочка для ранней эпохи (этап 6), метка, встреченная один раз
(вероятная опечатка, этап 2: `Content.warnings`). Каждая находка графа хранит проверку и записи, о которых
она (`findings`): из них реестр ставит итог проверки записи, а `content-checks.md` — сводку с тем, как
исправить.

Мир с частью бандлов (этап 7а, сделано): рецепт, которому нужен инструмент класса, которого нет ни у одного
предмета мира, не узнают и не показывают (`Crafting.possible`; рецепт ножом в мире без бандла ножа). Станок
рецепта в мире всегда есть: `at` — жёсткая ссылка, без бандла станка выпадает и бандл рецепта. Проверка
каждого бандла отдельно (она уже есть в `tools/validate.gd`) следит, что мир без чужих бандлов работает.
Прежняя `Crafting.reachable` считала бревно, камень и руду доступными без топора и кирки; с этапа 4 её нет,
валидатор идёт через граф, а `tests/progress_test.gd` остаётся проверкой игрой.

## 12. Загрузка и регистрация

Порядок прежний: `Content` читает бандлы, `resolve` упорядочивает их и выключает лишённые зависимостей, записи
проверяются схемой, накладываются патчи, проверяются ссылки, реестры заполняются в
`Mods._refresh_registries` (с этапа 4 и реестр старта `Starts`). Граф строят только валидатор, отчёты и тесты: игре на
телефоне он не нужен, и загрузка мира не дорожает. Эпохи нужны только графу и отчётам, реестра в игре у них
нет. Новый вид данных добавляется как сейчас: схема в `SCHEMAS`, реестр с `refresh()` (если вид нужен игре),
строка в `_refresh_registries`, проверка в `tools/validate.gd`.

Сколько это стоит (этап 8, `tools/bench_content.gd`, ПК без экрана): 219 записей нынешних модов читаются
за 41 мс и загружаются за 14 мс; с придуманным модом на 800 записей (1019 всего) — 122 и 64 мс, то есть
растёт линейно, запас под сотни записей эпох есть. Поиск записи по id теперь по указателю (перебором тысяча
записей загружалась 105 мс). Телефон медленнее раз в десять; его числа — строка «Загрузка» в «Данных для
теста» (`Content.read_ms`, `load_ms`). С 2026-11-01 (холодный старт, решение 155) разобранный YAML
собирается при экспорте в `content_cache.bin` (`tools/content_cache.gd`, `Content.PARSED`), и сборка не
разбирает YAML на телефоне ([systems/content.md](../systems/content.md), «Сколько стоит»).

## 14. Старые миры и дополняющие бандлы (этап 7а, решение 4А, сделано)

Дополняющий бандл — тот, в котором только предметы, рецепты, эпохи, старт и звуки (нет ячеек, деревьев,
кустов, растений, биомов, зверей; `Mods.additive`, и по его записям, и по патчам). Он сам входит в старый мир,
где включён его мод, если мир его ещё не видел и в мире есть всё, что ему нужно: `world.json` запоминает
(`known`), какие бандлы существовали при сохранении, поэтому бандл, выключенный игроком, выключенным и
остаётся. Мир, сохранённый до `known`, знал дополняющие бандлы списка `Mods.OLD_ADDITIVE` (факел — с метки
`content` 9). Земля и номера материалов не меняются. Ручного списка в `src/client/save_game.gd` больше нет:
набор мира по его `world.json` решает общий `Mods.of_world` (им же откроет миры сервер). Бандл с ячейками,
деревьями или зверями в старый мир не входит: он меняет землю и номера материалов.

Бандл, выпавший из набора нового мира, на экране «Моды» показывает всю причину строкой под собой: у
верстака без волокна — «нужен «Дерево», а ему «Волокно»» (`Mods.why`: чего не хватает ему, чего — тому, до
выключенного).

| новый ресурс и его источники | предмет + поле у источника (`gives`, `log`, `bonus`…) | нет |
| ещё один источник старого ресурса | поле у нового объекта со ссылкой на тот же id | нет |

| рецепт, альтернативный рецепт | запись `recipes` | нет |

Что строки «без кода» правда добавляются одними данными, проверяет приёмочный тест
`tests/unit/bundle_system_test.gd` (этап 8): мод-пример «Лён» и «Ткацкий станок», написанный по README, — новый
ресурс и семя с двумя источниками (куст: сорвать руками, выкопать лопатой; побочное при трёпке), ещё один
источник старого волокна, куст на лугу патчем биома, нож нового класса, станок, который заменяет верстак,
рецепт с нерасходуемым челноком, износом ножа и побочным, альтернатива руками, эпоха «Ткачество», патч старта
(волокно в сумке, руки достают дальше) — загружается без ошибок, граф доходит до всего со старта и выводит
эпохи, а в игре лён рвут, треплют, ткут на станке, и у станка делают рецепт верстака. Каждый бандл мода
грузится в одиночку, а без верстака бандл станка выпадает с причиной. Деревья и звери с готовыми ролями
проверяют бандлы самих модов (`validate.gd`: каждый бандл в одиночку).

По шагам и с примерами YAML (этап 7б): `content/core/README.md` — старт, умения рук, эпоха;
`content/tools/README.md` — инструмент нового класса, станок, рецепт и альтернатива;
`content/resources/README.md` — ресурс и ещё один источник старого ресурса.

## 16. Правила качества

1. **Совместимость.** Старые сохранения открываются (`tests/save_test.gd`), игра проходит тем же путём
   (`tests/progress_test.gd`); то, что видит игрок, меняется только с согласия пользователя.
2. **Без дублей.** Новое строится на нынешних механизмах (виды, схемы, ссылки, патчи, роли); новый механизм —
   только если нынешний не подходит, с решением в журнале.
3. **Один формат.** Id и имена — по разделу 3; ссылка всегда по id, с типом связи в схеме.
4. **Нет тупиков и циклов.** С этапа 4 граф проверяет каждый PR: всё достижимо со старта, блокирующих
   циклов нет.
5. **Ссылки проверяются.** Схема, битые ссылки, тип связи у каждой ссылки, молчаливые повторы — ошибки.
6. **Игровые данные — не в коде.** Числа, списки и имена контента живут в YAML; движок знает классы и флаги,
   а по id называет только записи ядра.
7. **Расширяемость и баланс.** Предварительные числа помечены `provisional`; баланс — правка данных;
   альтернатива — ещё один рецепт, а не исключение в коде.
8. **Решения записаны.** Журнал `plan/README.md`, [DECISIONS.md](../DECISIONS.md), этот документ и таблица
   этапов обновляются в том же PR, что код.
9. **Тесты после каждого этапа.** Все проверки из `CLAUDE.md` (с этапа 3 ещё свежесть отчётов) и новый тест,
   который падает без нового кода.

## 17. Чего система не делает

- Технологий, очков и дерева исследования (решение 2В).
- Скриптов и правил в данных: новое действие в мире — код вместе с механикой (решение 3А).
- Механик топлива печей, энергии, брони, животноводства: они приходят со своими эпохами контента (охота,
  одежда, урон, стрельба и несколько руд уже есть).
- Массового контента: каталог эпохи сначала утверждает пользователь, потом её бандлы и рецепты.
