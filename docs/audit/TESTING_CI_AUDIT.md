## 2. Что работает нестабильно

Данные — журналы Actions за два дня.

| Проверка | Провалы | Разбор |
|---|---|---|
| `frame_test`: «idle: a frame takes under 1/20 of a chunk» и то же у костра | 14 из 70 прогонов `frames` (0,97 при пределе 0,81; 1,15 при 1,03; 0,86 при 0,77) | предел — стоимость чанка / 20, чанк мерится один раз в начале. На машинах GitHub чанк стоит то 13–17 мс, то 20–25 мс (два вида машин), а кадр простоя — 0,6–1,1 мс почти независимо от этого: на «быстрой» машине доля выходит у самого предела. Плюс берётся среднее 120 кадров: одна заминка двигает его. Что идёт в кадре простоя, не печаталось |
| `frame_test`: «crafting materials:cord keeps the rest of a frame» | 2 | один кадр над пределом из 41 (допуск 1 на 250 кадров); ждать повтора |
| `progress_test`: «Медведь fell, but its Туша is not on the ground» | 1 | ожидание туши — 3 с по часам, а кадр на занятой машине бывает 2 с (в журнале фризы «браузер 2499 мс»): за 3 с проходит кадр-два, туша ещё не пришла клиенту |
| `progress_test`: «Сундук cannot be set down at the camp» | 1 (и 40 «made: …» за ним) | то же: 4 с отдыха по часам; первый провал обрывает весь путь, за ним валятся все рецепты |
| `progress_test`: предел 1200 с (exit 124) | 1 в CI; локально в контейнере — каждый раз | обычный прогон в CI 945 с — у самого предела, и путь растёт с контентом |
| Прогон `main` «cancelled» | регулярно | `cancel-in-progress` для всех веток: следующее слияние отменяет проверку предыдущего, поломка прячется |

За два дня (60 прогонов, 15 веток PR) 10 прогонов перезапускались «Re-run»; idle-проверка `frame_test` не прошла в 14 из 70 прогонов `frames`.

## 3. CI: что не так

1. **Самый долгий путь — `progress_test`, 945 с из ~16,5 мин прогона**; остальное укладывается в 3 мин.
   Он шёл одной машиной вместе с юнит-тестами, сохранением и сервером.
2. **Права токена** — `pages: write` и `id-token: write` на весь workflow, то есть и на задания,
   исполняющие код PR. Нужны только `deploy`.
3. **Сторонние действия по плавающим тегам** (`@v4`): закрепить на коммит.
4. **Godot скачивается без сверки контрольных сумм.**
5. **Логи тестов не сохраняются** (временная папка `run_all.sh` удаляется), итоги видно только в
   длинном журнале; в сводке запуска пусто.
6. **Нет быстрой проверки**: любая ошибка ищется после установки Godot и импорта (~20 с) и юнит-тестов.
   Скрипт, который не грузит ни один тест (инструменты, рисовалки), с ошибкой разбора проходит CI.
7. Нет `timeout-minutes` у заданий: зависшее задание держит машину 6 ч.
8. Предупреждения Node 20 у `actions/*@v4` — пока только предупреждение (обновление — в плане).
9. Ручной запуск (`workflow_dispatch`) есть; параметров не нужно.

## 4. Валидатор данных против раздела 4 ТЗ

| Требование | Где уже есть |
|---|---|
| уникальность id | `content.gd`: «duplicate id», замена только с `replaces: true` |
| нет отсутствующих ссылок, типы ссылок | схемы `ref:<вид>` (жёсткие и мягкие), `Crafting.check` (станок — станок), `Items.check` (`serves`, `place_tool`) |
| корректность рецептов, входы и выходы, количества | схема `recipes`: `count ≥ 1`, `amounts` — целые ≥ 1, `chance` 0..1, `time ≥ 0`, `wear` без инструмента — ошибка |
| инструменты и станки существуют | граф: «no item is a `<класс>`», станок без рецепта или источника |
| циклические зависимости | граф: «a blocking cycle» с вещами круга |
| недостижимые рецепты, тупики производства | граф: «can never be made», «can never be had», «has no source»; предупреждения «dead end» |
| технологические зависимости | эпохи: «early_era», «long_chain» |
| достижимость ключевых ресурсов | граф полного набора — всё от старта; `progress_test` — вызовами игры |
| формат данных по схеме | `Content.SCHEMAS`, проверка при загрузке |
| понятный отчёт | каждая строка — вид, id записи, поле, что не так; `docs/generated/content-checks.md` — с объяснением и тем, как исправить |
| запуск локально, в CI, перед выпуском данных | `tools/validate.gd`; CI на каждый пуш |

Пробелы: не было теста, что валидатор называет каждую ошибку рецепта именно по id и полю, и не было
генеративной проверки самого графа (случайные наборы против простого вычисления).

## 5. Ответы на вопросы аудита

1. **Работает:** юнит-тесты, сохранение, сервер, валидатор, отчёты контента, smoke-тест, публикация.
2. **Нестабильно:** idle в `frame_test`; ожидания по часам в `progress_test`; предел времени
   `progress_test`; отмена прогонов `main`.
3. **Нет:** линта и компиляции всех скриптов; сохранения логов и сводки; сверки сумм Godot;
   минимальных прав; генеративных тестов; хука перед коммитом.
4. **Дублирование:** существенного нет. Правило слоёв проверяется только в `content_test` — оставлено
   там. `validate` и `run_tests` оба грузят данные, но проверяют разное.
5. **Долго:** `progress_test` (945 с в CI); `run_tests` 50–130 с; остальное до 40 с.
6. **Параллельно:** все задания независимы; `progress_test` делится на две половины по рецептам
   (нужно ли добытое со зверя) — каждая строит свой мир с нуля.
7. **Только при изменении файлов:** уже так для `smoke` (шаблон путей `changes`). Остальное идёт
   всегда: пропуск тестов по списку файлов ненадёжен для этого проекта (данные модов меняют поведение
   кода, тест-мир и генератор связаны с контентом), и ТЗ этого не позволяет.
8. **Блокирует слияние:** все задания, кроме пропущенного `smoke`; публикация ждёт всех. Правило ветки в
   GitHub (required checks) ставит владелец репозитория — список в
   [../testing/CI_PIPELINE.md](../testing/CI_PIPELINE.md).

## 6. Замечено попутно (не тесты)

- В `progress_test` после переноса игрока далеко (рыбалка, вылазки) бывают кадры 2–6 с, почти всё —
  «браузер», то есть не в отмеченных частях кадра Main. В игре такого переноса нет, но то же может
  быть при входе в далёкий мир или телепорте из «Маркеров». Передано в план как задача для
  производительности.
