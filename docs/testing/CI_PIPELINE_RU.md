# CI: как устроен пайплайн

Английская версия: [CI_PIPELINE.md](CI_PIPELINE.md) (она основная, эта — копия).

Статус: ACTIVE. Файл: `.github/workflows/build.yml`, установка Godot — `.github/actions/godot/`.
Как запускать то же локально — [TESTING_GUIDE.md](TESTING_GUIDE_RU.md).

## Когда запускается

| Событие | Что идёт |
|---|---|
| PR (открыт, новый пуш, переоткрыт, поставлена метка) | всё, кроме (по заданию `changes`): проверки в браузере, если PR не трогает то, что браузер показывает иначе (метка `smoke` включает её); пути к каждому рецепту (`progress`), если PR не трогает ни контент, ни крафт: `data/`, `bundle.yaml`, `mod.yaml` модов, `src/shared/content/`, `actions_*.gd` рук, `world_actions`, `workshop`, `placed`, `craft_queue`, `inventory`, `felling`, `fishing`, `quality`, сам тест, `run_all.sh`, `.github/` (задания `progress (…)` тогда проходят сразу, их шаги пропущены; правило в другом месте, что обрывает путь, видно в прогоне `main`, и первый красный прогон называет слияние). Метка `full` включает всё |
| пуш в `main` (слияние PR) | всё, всегда: `main` — страховка для того, что PR пропустил, и для двух PR, зелёных по отдельности, но ломающих вместе (#513 + #514); при успехе всех заданий — публикация |
| вручную: Actions → Test and build → Run workflow | всё, как в `main`, без публикации (она только для `main`) |
| вручную: Actions → Playtest server → Run workflow | не проверка: `.github/workflows/playtest.yml` запускает сервер игры из `main` за туннелем Cloudflare на заданные минуты (до 300) с ботами (`--join … --bot`, `src/client/input/bot.gd`; по умолчанию тестовый мир, 3 бота, 120 минут, бесплатные предметы), ссылка для телефона — в шаге «Link for the phone: open this step» и статусом `playtest-link`, игра находит её сама («Тестирование» → «Подключиться к тестовому серверу»); мир не сохраняется |

Новый пуш в тот же PR отменяет его прошлый запуск. В `main` запуски не отменяются: каждое слияние
проверяется до конца, и поломка не прячется за следующим слиянием (раньше прогон слитого PR мог
оказаться «cancelled»).

## Задания

Все задания идут параллельно, каждое на своей машине (кроме `smoke`, которая ждёт web-сборку, и
публикации, которая ждёт всё). Быстрые падают первыми.

| Задание | Что делает | Время | Блокирует |
|---|---|---|---|
| `lint` | `tools/lint.py` (правила скриптов и текстов, Python, shell, JS, JSON, workflow) , `tools/doc_index.py --check` (пути в документах, свежесть индекса кода) и `tools/lang_check.py --strict en,ru` (каждый ключ есть по-английски и по-русски, русского текста в коде нет); без Godot | ~10 с | да |
| `checks` | `parse` (каждый скрипт компилируется, `tools/parse_check.gd`), `validate` (данные модов и каждый бандл отдельно), `report` (свежесть `docs/generated/content-*.md`) | ~1 мин | да |
| `tests` | `run_tests` (юнит-тесты), `save_test`, `server_test` бок о бок | ~3 мин | да |
| `progress (hunting)`, `progress (other)` | две половины `progress_test`: рецепты, которым нужно добытое со зверя, и остальные — на двух машинах | см. отчёт | да |
| `frames` | `frame_test` один на машине (меряет кадры) | ~1,5 мин | да |
| `export` | версия и «Что нового» (`build_info.py`), web-экспорт, патчи `web_patch.py` и `web_cache.py`; артефакт `survivium-web` | ~1 мин | да (для деплоя) |
| `pc` | экспорт Windows и Linux; артефакты `survivium-windows`, `survivium-linux` | ~1 мин | да (для публикации) |
| `android` | Android APK (arm64), подписанный ключом из секретов ([../systems/android.md](../systems/android_RU.md)); артефакт `survivium-android` | ~2 мин | да (для публикации) |
| `smoke (desktop / phone / upright)` | web-сборка в headless Chrome (`tests/browser_smoke.mjs`); телефоны рисуют самый лёгкий набор (`?quality=0`, `Settings.use_page_quality`), компьютер — обычную картинку | 1–4 мин | да, когда идёт |
| `release` | только `main`: релиз GitHub `v<этап>.<PR>` с заметками `tools/release_notes.py` (строки «Что нового» с прошлого релиза), APK и ПК-сборками; те же файлы — в пререлизы `android-latest`, `pc-latest` ([Релизы](#релизы)) | секунды | — |
| `deploy` | только `main`: web-сборка на GitHub Pages | секунды | — |

«Блокирует» здесь значит: `release` и `deploy` ждут его успеха, а по правилу проекта PR сливается только
при зелёном CI. Чтобы GitHub сам не давал слить красный PR, в настройках репозитория (Settings →
Branches → правило для `main` → Require status checks) отметьте задания `lint`, `checks`, `tests`,
`progress (hunting)`, `progress (other)`, `frames`, `export`, `pc`, `android`. `smoke (…)` туда не ставится: на PR
без изменений клиента оно пропускается.

## Релизы

Каждая сборка `main`, прошедшая все задания, — релиз на GitHub (Releases), его делает задание `release`:

- **Версия и тег.** Версия — та, что показывает игра, `<этап>.<PR>` (`tools/build_info.py`): этап —
  `application/config/version` в `project.godot`, PR — тот, что слил коммит (его заголовок кончается на
  `(#N)`). Это правильный semver: этап — минорная часть (поднимается вручную, когда закрыт этап MVP), PR —
  патч (только растёт). Тег — `v<этап>.<PR>` на слитом коммите, название — `Survivium <версия>`.
- **Заметки.** `tools/release_notes.py` берёт PR, слитые после тега прошлого релиза (`git log`, поэтому
  checkout со всей историей и тегами), и группирует их строки «Что нового» по видам: новое, улучшено,
  исправлено, оптимизировано, ядро; по-английски, потом по-русски; PR без таких строк — по заголовку. Дальше —
  загрузки и ссылка сравнения двух тегов. Без прошлого релиза заметки идут от начала этапа. Упавший прогон
  `main` релиза не делает: его изменения войдут в следующий.
- **Файлы.** `survivium-android.apk`, `survivium-windows.zip`, `survivium-linux.tar.gz` (имена не меняются,
  так что `https://github.com/randomboygh/survivium/releases/latest/download/<файл>` всегда даёт новейшую
  сборку). Web-сборка — Pages.
- **Latest.** Новейшая версия помечена «Latest»; прогон, кончившийся после более нового (прогоны `main` не
  отменяются), делает релиз без пометки и не трогает скользящие пререлизы.
- **Скользящие пререлизы.** `android-latest` и `pc-latest` — для старых ссылок: те же файлы, что у новейшего
  релиза, их теги переносятся на его коммит.
- Повторный прогон `main` правит свой релиз (заметки и файлы), а не падает.

## Результаты и логи

- В журнале задания каждая проверка — свёрнутая группа «имя: N с, exit код».
- Сводка запуска (страница запуска, вкладка Summary) — таблица каждой проверки: секунды, итог, строка
  счёта («3227 checks, 0 failed»), под ней первые строки `FAIL:` упавших.
- Упавшая проверка ставит аннотацию `::error` с первой строкой провала — видна прямо в PR.
- Логи каждой проверки — артефакт `logs-<задание>` (хранится 90 дней по умолчанию GitHub), даже если
  задание упало.
- Письмо о провале GitHub шлёт автору запуска сам (настройки уведомлений аккаунта).

## Безопасность

- Права токена по умолчанию — только чтение (`contents: read`); `changes`, `export`, `pc` читают ещё
  PR (`pull-requests: read`), `release` пишет релиз и его тег (`contents: write`), `deploy` — Pages
  (`pages: write`, `id-token: write`). Код PR не получает прав записи.
- Секреты: встроенный `GITHUB_TOKEN` и ключ подписи Android `ANDROID_KEYSTORE`, `ANDROID_KEYSTORE_PASSWORD`
  (их читает только задача `android`; файл ключа удаляется после экспорта); ни один не печатается.
- Сторонние действия — только `actions/*` GitHub, закреплены на коммит (SHA) с версией в комментарии.
  Обновлять — заменой SHA на коммит нового тега (`git ls-remote https://github.com/actions/<имя>`).
- Godot и шаблоны экспорта скачиваются с релиза движка и сверяются с SHA-512 из
  `.github/actions/godot/SHA512-SUMS`; для новой версии Godot туда добавляются две строки из
  `SHA512-SUMS.txt` её релиза, иначе задание падает с понятной ошибкой. Кэш ключуется версией и
  этими суммами.
- `playwright-core` для smoke-теста закреплён версией (`1.48.2`), без lock-файла.
- Каждый тест пишет в свой `user://` (`XDG_DATA_HOME`), сохранения разработчика не трогаются;
  внешних сервисов тесты не зовут (сервер-тест слушает localhost:7791).
- Проверка кода и публикация разделены: публикуют только `release` и `deploy`, только в `main`, только
  после успеха всех проверок.

## Время

Замеры до и после — [../audit/TESTING_CI_REPORT.md](../audit/TESTING_CI_REPORT.md). Самое долгое — путь до
каждого рецепта (`progress_test`); он поделен на две половины, идущие на двух машинах.
Каждое задание ограничено `timeout-minutes`, каждая проверка — своим пределом в `tests/run_all.sh`.

## Что делать, когда CI красный

1. Открыть сводку запуска: какая проверка и первые `FAIL:`.
2. Повторить ту же проверку локально: `GODOT=~/godot/godot tests/run_all.sh <имя>`.
3. `frame_test` и `progress_test` чувствительны к машине: в сообщении провала есть числа (мерка чанка
   рядом с замером, части кадра, места и кадры ожидания). Перезапуск задания допустим, только если числа
   показывают сбой машины, а не кода; иначе — чинить код. Каждый такой случай — строка в
   [TEST_COVERAGE.md](TEST_COVERAGE_RU.md), раздел «Нестабильные проверки».
4. После слияния следите за прогоном `main` до конца (правило проекта) и чините красный сразу.
