# CI: как устроен пайплайн

Английская версия: [CI_PIPELINE.md](CI_PIPELINE.md) (она основная, эта — копия).

Статус: ACTIVE. Файл: `.github/workflows/build.yml`, установка Godot — `.github/actions/godot/`.
Как запускать то же локально — [TESTING_GUIDE.md](TESTING_GUIDE_RU.md).

## Когда запускается

| Событие | Что идёт |
|---|---|
| PR (открыт, новый пуш, переоткрыт, поставлена метка) | всё, кроме (по заданию `changes`): проверки в браузере, если PR не трогает то, что браузер показывает иначе (метка `smoke` включает её); пути к каждому рецепту (`progress`), если PR не трогает ни контент, ни крафт: `data/`, `bundle.yaml`, `mod.yaml` модов, `src/shared/content/`, `actions_*.gd` рук, `world_actions`, `workshop`, `placed`, `craft_queue`, `inventory`, `felling`, `fishing`, `quality`, сам тест, `run_all.sh`, `.github/` (задания `progress (…)` тогда проходят сразу, их шаги пропущены; правило в другом месте, что обрывает путь, видно в прогоне `main`, и первый красный прогон называет слияние). Метка `full` включает всё |
| пуш в `main` (слияние PR) | всё, всегда: `main` — страховка для того, что PR пропустил, и для двух PR, зелёных по отдельности, но ломающих вместе (#513 + #514); при успехе всех заданий — публикация. Единственное исключение: если всё, что изменилось с релиза, помеченного Latest, — документы (`docs/`, Markdown-файл в корне, шаблон PR: ничто из этого не попадает в сборку, `tools/docs_only.py`), задание `changes` говорит `build=false` и идёт только `lint` — ни тестов, ни сборок, ни релиза, ни выкладки (прогон PR проверил документы; один #949 занял 13 минут и сделал релиз в 169 МБ) |
| вручную: Actions → Test and build → Run workflow | всё, как в `main`, без публикации (она только для `main`) |
| вручную: Actions → Playtest server → Run workflow | не проверка: `.github/workflows/playtest.yml` запускает сервер игры из `main` за туннелем Cloudflare на заданные минуты (до 300) с ботами (`--join … --bot`, `src/client/input/bot.gd`; по умолчанию тестовый мир, 3 бота, 120 минут, бесплатные предметы), ссылка для телефона — в шаге «Link for the phone: open this step» и статусом `playtest-link`, игра находит её сама («Тестирование» → «Подключиться к тестовому серверу»); мир не сохраняется |

Новый пуш в тот же PR отменяет его прошлый запуск. В `main` запуски не отменяются: каждое слияние
проверяется до конца, и поломка не прячется за следующим слиянием (раньше прогон слитого PR мог
оказаться «cancelled»).

## Задания

Все задания идут параллельно, каждое на своей машине (кроме `smoke`, которая ждёт web-сборку, и
публикации, которая ждёт всё). Быстрые падают первыми.

| Задание | Что делает | Время | Блокирует |
|---|---|---|---|
| `lint` | `tools/lint.py` (правила скриптов и текстов, Python, shell, JS, JSON, workflow, существуют файлы, которые перечисляет `hand`, look.yaml деревьев сверяется с их картинками: `tools/tree_feet.py --check`, предварительно ставится Pillow), `tools/doc_index.py --check` (пути в документах, свежесть индекса кода) и `tools/lang_check.py --strict en,ru` (каждый ключ есть по-английски и по-русски, русского текста в коде нет); без Godot | ~10 с | да |
| `checks` | `parse` (каждый скрипт компилируется, `tools/parse_check.gd`), `validate` (данные модов и каждый бандл отдельно), `report` (свежесть `docs/generated/content-*.md`), `balance` (свежесть `docs/balance/GAME_BALANCE_TABLES.md`, `tools/balance_report.gd --check`) | ~1 мин | да |
| `tests` | `run_tests` (юнит-тесты), `save_test`, `server_test` бок о бок | ~3 мин | да |
| `progress (hunting)`, `progress (metal)`, `progress (other)` | три части `progress_test` на трёх машинах: рецепты, которым нужно добытое с животного (туша, рыба), те, которым нужна руда, и остальные; выбраны по измеренному времени (ниже) | ~4,5, ~8, ~12,5 мин | да |
| `frames` | `frame_test` один на машине (меряет кадры) | ~1,5 мин | да |
| `export` | версия и «Что нового» (`build_info.py`), web-экспорт, патчи `web_patch.py` и `web_cache.py`; артефакт `survivium-web` | ~1 мин | да (для деплоя) |
| `pc` | экспорт Windows и Linux; артефакты `survivium-windows`, `survivium-linux` | ~1 мин | да (для публикации) |
| `android` | Android APK (arm64), подписанный ключом из секретов ([../systems/android.md](../systems/android_RU.md)); артефакт `survivium-android` | ~2 мин | да (для публикации) |
| `smoke (desktop / phone / upright)` | web-сборка в headless Chrome (`tests/browser_smoke.mjs`); телефоны рисуют самый лёгкий набор (`?quality=0`, `Settings.use_page_quality`), компьютер — обычную картинку | 1–4 мин | да, когда идёт |
| `release` | только `main`: релиз GitHub `v<этап>.<PR>` с заметками `tools/release_notes.py` (строки «Что нового» с прошлого релиза), APK и ПК-сборками; те же файлы — в пререлизы `android-latest`, `pc-latest`; для одних документов релиза нет; удаляет все, кроме 50 новейших и последнего релиза каждого этапа ([Релизы](#релизы)) | секунды | — |
| `deploy` | только `main`: web-сборка на GitHub Pages, по одной выкладке за раз (`concurrency: pages`) и только новейшей сборки `main`: её новейшего коммита или того, за которым идут только слияния документов (они ничего не собирают): старый прогон, кончившийся поздно или перезапущенный, Pages не трогает | секунды | — |

«Блокирует» здесь значит: `release` и `deploy` ждут его успеха, а по правилу проекта PR сливается только
при зелёном CI. Чтобы GitHub сам не давал слить красный PR, в настройках репозитория (Settings →
Rules → Rulesets → «main protection», https://github.com/randomboygh/survivium/settings/rules/27271944 →
Require status checks to pass; классического правила ветки нет) отметьте задания `lint`, `checks`, `tests`,
`progress (hunting)`, `progress (metal)`, `progress (other)`, `frames`, `export`, `pc`, `android`. `smoke (…)` туда не ставится: на PR
без изменений клиента оно пропускается.

## Релизы

Каждая сборка `main`, прошедшая все задания, — релиз на GitHub (Releases), его делает задание `release`:

- **Версия и тег.** Версия — та, что показывает игра, `<этап>.<PR>` (`tools/build_info.py`): этап —
  `application/config/version` в `project.godot`, PR — тот, что слил коммит (его заголовок кончается на
  `(#N)`). Это правильный semver: этап — минорная часть (поднимается вручную, когда закрыт этап MVP), PR —
  патч (только растёт). Тег — `v<этап>.<PR>` на слитом коммите, название — `Survivium <версия>`.
- **Заметки.** `tools/release_notes.py` берёт PR, слитые после тега прошлого релиза (`git log`, поэтому
  checkout со всей историей и тегами), и группирует их строки «Что нового» по видам: новое, улучшено,
  исправлено, оптимизировано, ядро; по-английски, потом по-русски; PR без таких строк — по заголовку. Дальше —
  загрузки и ссылка сравнения двух тегов. Без прошлого релиза заметки идут от начала этапа. Упавший прогон
  `main` релиза не делает: его изменения войдут в следующий.
- **Файлы.** `survivium-android.apk`, `survivium-windows.zip`, `survivium-linux.tar.gz` (имена не меняются,
  так что `https://github.com/randomboygh/survivium/releases/latest/download/<файл>` всегда даёт новейшую
  сборку). Web-сборка — Pages, рядом с ней лежит `latest.json` (`build_info.py --latest`: версия, когда слит её PR,
  её 100 новейших изменений): каждая сборка main через несколько секунд после показа меню спрашивает его и
  предлагает обновление в «Что нового» (`src/client/net/updates.gd`).
- **Latest.** Релиз новейшего слияния в `main` явно помечается «Latest» (`--latest=true`), каким бы ни был его
  номер: PR, открытый рано и слитый поздно (#603 после #623), имеет меньший номер, но это новейшая сборка.
  «Новее» считается по истории (`git tag --contains HEAD`); прогон, кончившийся после прогона более позднего
  слияния (прогоны `main` не отменяются), делает релиз без пометки и не трогает скользящие пререлизы. Заметки
  идут от ближайшего по истории тега релиза, а не от наибольшего номера.
- **Скользящие пререлизы.** `android-latest` и `pc-latest` — для старых ссылок: те же файлы, что у новейшего
  релиза, их теги переносятся на его коммит.
- Повторный прогон `main` правит свой релиз (заметки и файлы), а не падает.
- **Для одних документов релиза нет.** Слияние в `main`, изменившее с релиза, помеченного Latest, только документы,
  ничего не собирает и релиза не делает ([Когда запускается](#когда-запускается)); его строки «Что нового» попадают в
  заметки следующего релиза, которые начинаются от тега последнего релиза. «С Latest», а не «этот коммит»: так что
  слияние кода, чей ожидающий прогон заменил прогон слияния документов, всё равно выпускается прогоном слияния
  документов. Pages хранит последнюю сборку, поэтому проверка обновления игры (`latest.json`) никогда не предложит
  версию, у которой нет релиза.
- **Старые релизы удаляются.** После релиза `tools/prune_releases.py --keep 50` оставляет 50 новейших
  `v<этап>.<PR>` (по версии), последний релиз каждого этапа (тот, что его закрыл: `v0.3.777`, `v0.4.904`), помеченный
  «Latest», только что сделанный и скользящие пререлизы; любой другой релиз удаляется вместе с тегом (выбор
  владельца, 2026-11-27), самые старые первыми и не больше 30 за прогон (`--max`: GitHub ограничивает токен
  примерно 80 записями в минуту, по две на релиз), так что накопившееся убирается за несколько прогонов. Неудачное
  удаление только пишется в журнал и ждёт следующего прогона.
  `--dry-run` печатает список без удаления (`GH_TOKEN`, `GITHUB_REPOSITORY`; только REST).

## Результаты и логи

- В журнале задания каждая проверка — свёрнутая группа «имя: N с, exit код».
- Сводка запуска (страница запуска, вкладка Summary) — таблица каждой проверки: секунды, итог, строка
  счёта («3227 checks, 0 failed»), под ней первые строки `FAIL:` упавших.
- Упавшая проверка ставит аннотацию `::error` с первой строкой провала — видна прямо в PR.
- Логи каждой проверки — артефакт `logs-<задание>` (хранится 90 дней по умолчанию GitHub), даже если
  задание упало.
- Письмо о провале GitHub шлёт автору запуска сам (настройки уведомлений аккаунта).

## Безопасность

- Права токена по умолчанию — только чтение (`contents: read`); `changes`, `export`, `pc` читают ещё
  PR (`pull-requests: read`), `release` пишет релиз и его тег (`contents: write`), `deploy` — Pages
  (`pages: write`, `id-token: write`). Код PR не получает прав записи.
- Секреты: встроенный `GITHUB_TOKEN` и ключ подписи Android `ANDROID_KEYSTORE`, `ANDROID_KEYSTORE_PASSWORD`
  (их читает только задача `android`, и только в сборке `main`: APK из PR подписывается ключом, сделанным для
  его прогона; файл ключа удаляется после экспорта); ни один не печатается. PR запускает файл workflow своей
  ветки, так что ключ закрыт от прогона PR, пока ветки пушит только владелец; защищённое окружение держало бы
  его и тогда.
- Сторонние действия — только `actions/*` GitHub, закреплены на коммит (SHA) с версией в комментарии,
  каждое на версии, работающей на Node 24. Обновлять — заменой SHA на коммит нового тега
  (`git ls-remote https://github.com/actions/<имя> 'refs/tags/<тег>^{}'`).
- Инструменты закреплены: образ машины `ubuntu-26.04` (не `ubuntu-latest`), Android build tools `35.0.0`,
  которые подписывают и проверяют APK (ставятся, если в образе их нет). Chrome smoke-теста — машинный; его версия
  печатается в логе.
- `cloudflared` тестового сервера сверяется с `CLOUDFLARED_SHA256` в `playtest.yml`: для новой
  `CLOUDFLARED_VERSION` туда нужна её сумма (`sha256sum` скачанного `cloudflared-linux-amd64`).
- Godot и шаблоны экспорта скачиваются с релиза движка и сверяются с SHA-512 из
  `.github/actions/godot/SHA512-SUMS`; для новой версии Godot туда добавляются две строки из
  `SHA512-SUMS.txt` её релиза, иначе задание падает с понятной ошибкой. Кэш ключуется версией и
  этими суммами.
- `playwright-core` для smoke-теста закреплён версией (`1.64.1`), без lock-файла.
- Каждый тест пишет в свой `user://` (`XDG_DATA_HOME`), сохранения разработчика не трогаются;
  внешних сервисов тесты не зовут (сервер-тест слушает localhost:7791).
- Проверка кода и публикация разделены: публикуют только `release` и `deploy`, только в `main`, только
  после успеха всех проверок.

## Время

Замеры до и после — [../audit/TESTING_CI_REPORT.md](../audit/TESTING_CI_REPORT.md). Самое долгое — путь до
каждого рецепта (`progress_test`); он поделен на три части, идущие на трёх машинах
(`--part`, см. `_part` в тесте). Каждое задание ограничено `timeout-minutes`, каждая проверка — своим пределом в
`tests/run_all.sh`, который предупреждает о проверке, прошедшей за 3/4 своего предела (`::warning` на прогоне).

Как выбирались части (аудит TEST-1, 2026-11-27). Две половины, «нужен зверь» и остальные, были далеки от равных:
на main `progress (hunting)` занимал 124–174 с, а `progress (other)` 750–1393 с, в худшем случае 93 % своего предела
1500 с, — длинный полюс каждого прогона. По времени рецепт за рецептом стоимость остальных была в их вылазках (54):
рыба (~135 с), кирпичные станки (домница, камин, кузница), плавка (железо, платина, сталь, кирпичная печь, фонарь),
стекло окон и ягоды красителей. Каждая часть делает то, что нужно её рецептам, с пустой сумкой, поэтому часть платит
снова за то, что делит с другой (лагерь, кирпичные станки); разделённые по тому, что нужно (туша или улов животного,
затем руда, затем остальное), они делят мало. Локально (три бок о бок на 4 ядрах) и на прогоне PR #954, каждая на
своей машине:

| часть | рецептов | вылазок | локально | CI |
|---|---|---|---|---|
| до: `other` | 194 | 54 | 1035 с | 750–1393 с |
| до: `hunting` | 30 | 6 | 89 с | 124–174 с |
| `hunting` (звери и рыба) | 37 | 6 | 220–231 с | 217 с |
| `metal` (нужна руда) | 54 | 29 | 440–455 с | 418 с |
| `other` | 133 | 30 | 510–517 с | 685 с |

Часть кончается перечнем самых медленных рецептов (`slowest: …`): когда одна переходит ~1100 с (3/4 предела), снова
разделить по ним. Перенос станка, который нужен рецептам только одной части, в эту часть (домница в `metal`) ничего
не сэкономил: первый кирпичный станок, который делает часть, платит за вылазки за глиной и камнем, каким бы он ни был.

## Что делать, когда CI красный

1. Открыть сводку запуска: какая проверка и первые `FAIL:`.
2. Повторить ту же проверку локально: `GODOT=~/godot/godot tests/run_all.sh <имя>`.
3. `frame_test` и `progress_test` чувствительны к машине: в сообщении провала есть числа (мерка чанка
   рядом с замером, части кадра, места и кадры ожидания). Перезапуск задания допустим, только если числа
   показывают сбой машины, а не кода; иначе — чинить код. Каждый такой случай — строка в
   [TEST_COVERAGE.md](TEST_COVERAGE_RU.md), раздел «Нестабильные проверки».
4. После слияния следите за прогоном `main` до конца (правило проекта) и чините красный сразу.
